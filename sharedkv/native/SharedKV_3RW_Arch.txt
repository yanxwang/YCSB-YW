SharedKV Architecture Specification: 3 Read/Write Traditional Message Passing
Version: 1.2 (Strict Specification for Claude Code)

1. DESIGN PHILOSOPHY
* **Data-In-Message**: Key and Value data are physical payloads within the control message and are copied across SPSC queues.
* **Single-Writer Hash Table**: Requests are routed by hash(key) % m, ensuring only one designated Worker writes to any specific bucket, so zero write contention.
* **Linearizability**: Guaranteed by a central Synchronizer assigning global_seq_no.
* **Offset-Based Chaining**: All internal links use 64-bit relative offsets instead of absolute pointers.\

2. THREAD TOPOLOGY & CPU PINNING
* **Synchronizer (CPU 0)**: Global Sequencer, Router, and Data Copier.
* **Poller (CPU 1)**: Monitors response arrays and dispatches UINTR signals.
* **Request Thread j (CPU [2, 1+n])**: Populates messages with KV data and pushes to RequestQueue[j].
* **Worker Thread i (CPU [2+n, 1+n+m])**: Exclusive executor for its assigned hash buckets.
* **Response Thread j (CPU [2+n+m, 1+2n+m])**: Polls dedicated 2D response arrays for client j.

3. PHYSICAL DATA STRUCTURES (CXL MEMORY)
* **Request Queues [depth]**: n independent SPSC Ring Buffers (Request thread writes, Sync reads). 
* **Worker Rings [depth]**: m independent SPSC Ring Buffers (Sync writes, Worker reads).
* **Response Queues [m][depth]**: n sets of 2D arrays; each contains m SPSC queues.
  - Worker i writes to ResponseQueue[i][ ].
* **CXLSharedHashTable**: Partitioned by Worker ID; offset-based bucket linking.
* **DataRegion Partitioning**: Split into m segments; Worker i owns DataRegion[i] for lock-free allocation.

4. DATAFLOW & MEMORY BARRIERS (3 R/W PATH)
* **Step 1 (Write 1)**: Request Thread j writes full CXLKVMessage. Execute _mm_sfence().
* **Step 2 (Read 1/Write 2)**: Synchronizer reads message, assigns seq_no, and copies full payload to WorkerRing[i]. Execute _mm_sfence().
* **Step 3 (Read 2/Write 3)**: Worker i reads payload, performs KV op in private DataRegion, writes result to ResponseQueue[j][i]. Execute _mm_sfence().
* **Step 4 (Read 3)**: Response Thread j polls and reads results.

2. IMPLEMENTATION PRIMITIVES & HARDWARE BARRIERS
* **Writer (Worker)**: MUST execute _mm_sfence() after initializing a new node but BEFORE linking it to the bucket head or a previous node's next_offset.
* **Reader (GET Thread)**: MUST execute _mm_lfence() before reading bucket.head_offset to prevent CPU reordering and ensure visibility of the latest writes.
* **Visibility**: Hardware barriers are mandatory for cross-host/cross-socket cache visibility.


5. DATA STRUCTURE DEFINITIONS (C++)
struct alignas(64) CXLKVMessage {
    uint64_t global_seq_no;
    uint32_t client_id;
    uint8_t op_type; // 1:GET, 2:PUT, 3:UPDATE, 4:DELETE
    uint32_t key_len;
    uint32_t val_len;
    char key[128];
    char value[1024]; // Payload copied throughout stages
};

struct alignas(8) CXLBucket {
    uint64_t head_offset; // Relative to DataRegion base
};

struct alignas(64) CXLNode {
    uint64_t next_offset;
    uint32_t key_len;
    uint32_t val_len;
    char data[]; // Key followed by Value
};

6. HASH TABLE: COLLISION & RECLAMATION (SINGLE-WRITER MODE)
* **Collision Resolution**: Offset-based singly linked list (Chaining).
* **Memory Reclamation**: Each Worker i maintains a private 'free_list_head' (offset) in CXL memory.
  - On DELETE or UPDATE: The old node's next_offset is pointed to free_list_head; then free_list_head is updated to the old node's offset.
  - On PUT: Worker i first checks its free_list_head. If non-zero, it reuses the node; otherwise, it increments its private current_alloc_offset.
  - Property: Allocation and reclamation are O(1) and completely lock-free.

7. GET CONCURRENCY CONSISTENCY
* **Protocol**: "Initialize-then-Link".
* **Worker (Writer) Steps**:
  1. Allocate/Reuse node from private DataRegion[i] or FreeList.
  2. Fill Key, Value, and set next_offset = bucket.head_offset.
  3. _mm_sfence().
  4. Update bucket.head_offset = new_node_offset.
* **Response Thread (Reader) Steps**:
  1. _mm_lfence().
  2. Read bucket.head_offset.
  3. Traverse chain using next_offset.
  4. Rationale: Ensures readers never see a partially initialized node.

8. SHUTDOWN PROTOCOL (PIPELINE DRAIN)
1. Signal Request Threads to stop.
2. Synchronizer continues until all RequestQueues are empty.
3. Workers process until WorkerRings are empty.
4. Response Threads exit after ResponseQueues are empty (write_idx == read_idx).

5. PHYSICAL DATA STRUCTURES & TOPOLOGY
- CPU Pinning: Sync (0), Poller (1), Req (2..1+n), Worker (2+n..1+n+m), Resp (2+n+m..1+2n+m).
- Queues: RequestQueues [n], WorkerRings [m], ResponseQueues [n][m] (all SPSC).

6. DATAFLOW (3 R/W PATH)
- ReqTh (Write1) -> Sync (Read1/Write2) -> Worker (Read2/Write3) -> RespTh (Read3).
